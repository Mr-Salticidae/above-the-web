图表交付的确定性：坐标绘制胜过自动布局

一句话律：当顺序或位置本身是信息时，图的布局不能外包给引擎。 引擎优化的是交叉数，不是你的叙事顺序。

入档:2026-11-19 来源:《虚拟游戏》人物关系图三轮返工（私有 fence → Mermaid → Pillow 坐标绘制） 验证状态:三次连踩同一根因，属流程性硬伤，结论可直接入规范

一句话

我把「图长什么样」交给了三种外部机制——私有代码块、Mermaid 的 dagre、方向参数——三次都得到了一个「结构对、位置错」的结果。第四次放弃自动化，用坐标逐点钉死，一次通过。

三种承载的取舍

承载优点失效方式何时用
私有 fence（如 relation-graph）信息密度高、可交互渲染器不认 → 原样摊成源码（5,500 字符 JSON 铺满屏）只在确认对方用同一套工具的封闭环境
通用引擎（Mermaid / Graphviz）谁都认识、改起来快布局由引擎决定：无入边的节点被推到起始列、分区顺序被打乱；改 LR/TB 只是换一种自动布局结构对就行、位置无所谓的图
坐标绘制（Pillow / SVG 手排）位置与顺序完全可控、可复现要自己算坐标、自己要肉眼验收顺序与位置承载信息的图（分区、先后、层级）

引擎为什么不可控

dagre 的排布目标是「最小化连线交叉 + 按入边分层」。由此推出两条必然结果：

  1. 无入边的节点被推到最左/最上——它在图里没有「上游」，引擎就把它当起点。关系图里那个只有出边的旧角色因此抢到了 A 区前面。
  2. 方向参数不是控制点——LR 与 TB 只是两套自动布局，换方向等于换姿势，不改变「谁先谁后」的判定逻辑。

判据：如果改一次参数后没达到预期且原因说不清，就不要再调参数了，换承载方式。

坐标绘制怎么做（实测有效）

  • 分区先定 y 带：A 区 y≈180–420、B 区 y≈730–1000，区与区之间留出标题带；区内再定 x。
  • 名字框宽度按实测文字宽度给：长名字（「林建国＝华叔＝何建浩」）单独加宽，别用统一宽度硬塞。
  • 跨区连线走直角绕行：从源节点底部出、目标节点底部进，避开中间节点，不要用弧线穿过别人的框。
  • 画布留富余：右侧与底部各留 40px 以上，图例和注释才有地方放。

标注规范四条（都在这一轮踩过）

#规范反面教材
1状态用通用视觉惯例：划掉、加粗、置灰†（dagger）在中文语境被读成十字架，且与「灰底＝已死」图例自相矛盾
2不用西文符号承载中文语义已死就写「已死 / 已亡」，或直接打红线
3图例 ≥ 3 条一律动态排版：按 textlength 实测宽度推进固定 x += 170，长文案直接撞上下一个图例
4分类编码控制在两种以内，且互不重叠同时用「灰底=死」「金框=玩家」「†=死」，一个符号背两层信息

验收三步

  1. 看最终载体，不看源码：导出 PNG/PDF 后自己看一眼。
  2. 裁剪放大局部：名字是否溢出框、标签是否压线、图例是否重叠——全图缩略看不出来。
  3. 问一句「这个符号什么意思」：如果需要一个图例才能懂，就说明它没自解释。

资源随仓库

文档一旦声明「自包含」，图就必须跟着仓库走。常见坑：仓库 .gitignore 把 *.png 全排除了，图片引用看着没问题，别人克隆下来是断链。

做法：在 .gitignore 末尾开精确到文件的例外，而不是把整个目录放进来。

触发判据（何时该坐标画）

  • 图里有分区，且分区先后有含义（主干 → 外围、案发 → 调查）；
  • 图里有层级或时间顺序，读者要按顺序读；
  • 同一张图要反复出图、每次必须一致（对外交付、平台备案）；
  • 已经因为「位置不对」返工过一次。

任一命中 → 直接坐标绘制，别从 Mermaid 开始试。
