二、结果：做到什么、没做到什么

做到的（事实项）

  • 网页 Canvas 逐帧确定性录制：Playwright 在页面脚本加载前注入虚拟时钟，接管 performance.now/Date/requestAnimationFrame/setTimeout/setInterval，Math.random 固定种子；AudioContext 换 OfflineAudioContext 跟同一时钟走。同一 4 秒 PREVIEW 连录 3 次，120 帧逐帧哈希完全一致，原声两次差 -162 dB（浮点舍入）。
  • 三类镜头都走真实游戏逻辑：单人 6 条键盘自驾（往 keys 按 WASD/空格/Shift）；手机 2 条 390×844 视口 + CDP 原生多指触摸（F08 模拟 B站 App 容器的 4 个接口）；联机 2 条本机起同提交 server/server.js、3 个独立浏览器真实开房→输码→准备→开局。
  • 只拍真实机制：击杀、爆炸、金币吸附、商店结账、自动瞄准、无双都是游戏自己跑出来的。布置（跳波、快进无敌、给连击解锁武器、给金币）只用来快进到要拍的那一刻，诚实边界写进录制 README。
  • 卡点工具自洽：卡点.py（numpy + ffmpeg，无 librosa）合成 128/150/170 BPM 已知答案曲校验，BPM 误差 <1%，drop 差 <0.05 秒；修过反拍误判和半速误判。
  • 片长保护：剪辑_main.py 对卡点后变长、还没重录的镜头末帧定格补齐并标「短 x 秒·要重录」，片长不缩、音画不错位。
  • 诚实边界守住：封面/文案只说三人、不说流畅联机、不提 iOS；手机横屏/刘海功能过审后真机走查才发片。

没做到 / 留的尾

  • 首小时数据未回填：公开接口拿不到完播率，发布文案里「完播率 >30%、互动率 >3% 再投流」的判断缺一项。
  • 线上 Toy 与录制提交逐字节核对没做。
  • 上游两个 PR 未合并：线上版本比上游 main 新，要和作者对齐。
  • F08 容器是模拟的：只实现游戏用到的 4 个接口，真机效果靠作者走查，没对照 SDK 文档逐条核。
  • 三人联机只在本机跑通，没经公网。

三、方法论沉淀

网页 Canvas 游戏的逐帧确定性实录：接管页面时钟

核心：网页游戏做宣发片，画面既不录屏也不让 AI 画——在页面脚本加载前注入虚拟时钟接管 performance.now/Date/rAF/setTimeout/setInterval，Math.random 固定种子，AudioContext 换 OfflineAudioContext 跟同一时钟走；按 60Hz 推进每两步截一帧得 30fps，游戏原声录完一次离线渲染、帧对帧对齐。

来源：80 号 11 个镜头全部用这套录。

验证状态：⚠️ 首次（一个网页项目）。是 游戏宣传片实录_引擎逐帧录制与脚本代打_v1（77 号 Godot --write-movie）的网页对应实现，同一思路第二种引擎，算同向第二例。

操作规则：

  1. 时钟接管必须在游戏脚本之前注入（Playwright addInitScript）。dt 有上限（本作 0.033）时别用 30Hz 步长，会被夹慢约 1%，用 60Hz 两步一帧。
  2. 导出要发布的提交到独立副本录，录哪个 sha 记进录制记录，发片前和线上 Toy 版本核对。
  3. 布置（跳波、无敌、给金币、解锁武器）只用来快进到要拍那一刻；开录后画面里发生的事必须游戏自己跑，不改伤害判定、不摆假画面。
  4. 单人走键盘、手机走 CDP 原生触摸、联机本机起同提交服务端开多浏览器——都走游戏真实输入/网络路径。

边界：联机按真实时间限流，虚拟时间得按真实节拍推；只在这一个 Canvas 项目成立过。

宣发片「太短不像完整作品」：配乐留整首头尾、只删中间

核心：短宣发片让人觉得”不完整”，往往是配乐从歌中间截进来、结尾直接掐断。解法不是硬加镜头，而是用整首歌的头（前奏→主歌进入）和尾（尾声自然收），只剪掉中间重复的主歌/间奏段，让观众听到一首歌完整的起承转合。

来源：37.5 秒版作者判「不是完整作品」；改成保留整首头尾后 66.3 秒，作者「非常完美」。

验证状态：⚠️ 首次。与 音频也能蒙眼剪辑_突然静音是剪出来的_v1 同向——结构感是剪出来的。

操作规则：配乐剪辑.py 按小节线找「前奏+第一段主歌」做头、「尾声」做尾，中间重复乐段整节删除，接缝落小节线重拍 + 20ms 交叉淡化。片长由”要讲几个功能镜头”反推中间保留多少段。

观测手段本身要先被证伪（线上错误探针）

核心：装了错误探针不等于探针在工作。本作 08-21 加的全局错误探针因字符串里混进真换行整段解析失败，window.onerror 从没装上，线上红条一次都不可能出现——修好后要故意抛一次错确认红条真的出现，并补 HTML 内联脚本的语法解析测试（node --check 查不到 HTML 里的脚本）。

验证状态：⭐⭐ 与 沉默失败先装嘴律_够不到的环境先给它一层能看见的报错_v1 同一项目、同一探针的续例。

四、助手误判全记录

  1. ⚠️ 档案与本机工作副本对不上没第一时间察觉：档案写 BGM 在 feat/bgm/music.js/7051392，本机 D:\zombie-world 是从 fork 全新 clone、这些全不在、HEAD 也不对。开录前必须先核”要录哪个提交”，不能在对不上的工作区贸然开录。正解是按作者给的上游地址重新 clone 到固定本地路径。
  2. ⚠️ F01 字幕压住联机面板标题，来回取景三次：推近→整屏→整屏才解决，中间还有一次剪辑和录制并行跑、剪辑读到旧 F01。取景时就该给字幕预留位置，并发出片要串行化读写。
  3. ⚠️ C02 想当然拍”三人打 BOSS”：录了 60 秒 BOSS 都没走到三人附近，改成”三人守尸潮”并改镜头说明。AI 无法导演 NPC 走位，拍前先确认该局面在游戏里自然可达。
  4. ⚠️ 本轮最大的教训——长文档一次性写入反复撞后端 5xx：复盘主文档太长，连续多轮”现在一次性写进知识库”都在写入时被中断，空转十几轮没落盘一个字。正解是分段落盘：先 create 骨架+事实区，再多次 insert 追加各节，每段都短，中断也不丢已写部分。（见下方新方法论）

五、下次改进

  • 开工前先核对本机工作副本与档案记录的分支/提交/关键文件是否一致，对不上先停下来重新定位版本，再开录。
  • 大文档（复盘、长文案、长配置）默认分段写：骨架先落盘，再分节 insert，不要赌一次长写入能在超时前完成。
  • 宣发片配乐先想清楚”要讲几个功能镜头、片长下限多少”，再决定配乐留多长，避免先出短片再被打回重排全部镜头。
  • 发布后 24 小时内回填首小时数据（完播率只有创作者后台看得到）。

六、未知与未验证

  • 首小时完播率/互动率、“B站点开就玩”入场票的实际效果。
  • F08 容器真机表现（只过作者走查，没对 SDK 文档逐条核）。
