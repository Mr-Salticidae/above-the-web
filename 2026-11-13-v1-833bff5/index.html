对照一:计划书原案 vs 实际实现

计划书(docs/PROGRESS_SYNC_PLAN.md)写在动工之前,P1 落地时出现三处偏离。三处都不是”实现不了”,而是”原案会出事”:

原案实际为什么改
失败保留队列并重试失败只置状态,不自动重排默认 1.5 秒合批窗口会变成每 1.5 秒重打一次,服务端 5xx 时就是小型自我 DDoS
每轮扫全量 diff 找脏项存储层维护 dirty 集合,takeDirty() 取走即清全量 diff 在 8 项时无感,在长清单上是 O(n) 常驻开销;且下发数据会被反手再推形成乒乓,靠 applyRemote 返回 kept 拆掉
首次全量拉取后结束首次全量后补推本机存量项开关打开前勾的、从 v1 迁移来的,服务端都没有;不补推就永远只留在原设备

三处偏离全部回写进计划书,并把「实现时对计划的三处微调」单独成节。计划书是施工图,不是判决书——偏离如果不回写,下一篇复盘会照着错的图纸推因果。

对照二:本站既有账号系统

同一个站 7 月做过账号系统,当时沉淀过「内容归 git、状态归库的双源切分」。这次没有重新发明:

  • 体例直接复用:节点接口 Authorization: Bearer + localStorage、HttpError + reply()、审计只在破坏性操作记一笔。
  • 但有一处刻意的反向选择:账号系统的令牌是「会话」,有失效与主动踢出;进度同步的游标是每用户自增 rev,不认任何一方的时钟。理由是进度是「可合并的偏好」,不是「必须唯一有效的凭证」——用时间戳做合并键,等于把正确性押在用户设备时钟上。

方法论沉淀

稳定 ID 的迁移窗口,只有「第一次跨设备之前」

核心:只要数据要跨设备合并,主键就必须先稳定;用「列表里的第几项」当主键,在单机时代永远不会报错,在同步那天变成永久损坏。

来源:P0。11-12 的进度键是 caseId:index,第二天要同步时发现:8 个模块里删一个、插一个,老设备上的「第 3 项」就指向了另一个模块,而且没有任何报错——两端的勾选各自自洽,合并后谁都不知道错了。

验证状态:⚠️ 首次发现(单项目单次)。同类判断在 静态站接账号系统_内容归git状态归库的双源切分_v1 出现过弱形式(内容归 git 要有稳定 slug),但那次没有跨设备合并压力。

操作规则:

  1. 任何「会被合并到别处」的集合,主键先定 slug / UUID,不用下标。
  2. 给主键写一份写死的台账进测试(SLUG_LEDGER),改 slug 或删条目不报错就 CI 变红——那正是「有人在让老进度失效」的信号。
  3. 迁移要能回退:老格式原样备份成另一把键(-v1-backup),不覆盖。

反例/边界:纯展示型列表(渲染一次就丢、从不合并、从不回读)用下标没问题;一旦有「回读 + 对账」,立刻不适用。

本机没有记录,不等于用户没读过——空态是未知量,不是零

核心:「本机为空」是「我还不知道」,不是「答案是零」。任何在首轮拉取之前就写入默认值的逻辑,都会用默认值覆盖远端真值。

来源:P2 端到端实测抓到的真事故。阅读位置做到「打开 /juben/ 自动接着上次那一卷」:新设备首开时本地没有记录,代码落到默认第一卷并立刻 markReading('virtual-game') 写了一条;首轮拉取回来时,服务端那条「读到《窗边的女人》」比本机这条更旧,按 LWW 输了——B 机把用户在 A 机的真实阅读位置改成了「虚拟游戏」。双 context 实测直接复现,不是推演。

验证状态:⚠️ 首次发现,但性质上是同族第三形态(见下条「留位钩子」)。

操作规则:

  1. 分清三态:未加载 / 加载后为空 / 有值。未加载时什么都不写,不落默认值。
  2. 首次同步回来之前,界面可以显示默认卷,但不许把默认卷写进存储;写操作要等 settle 之后。
  3. 用户显式点过(本次用 userPicked 标记)就不再自动跳——人的动作优先级高于任何自动落位。
  4. 验收必须用「新设备首开」这个场景,单设备刷新永远测不出来。

反例/边界:纯本地、不同步的功能没有这个问题,默认值随便写;一旦引入「服务端可能更新」,立刻适用。

给页面留位的钩子,要挂在「元素出现」上,不挂在「用户行为」上

核心:布局补偿(给 fixed 元素留白、给滚动容器留高)如果只在「用户点了某个按钮」的回调里生效,那么从没点过的用户永远缺这段布局——而作者本人一定点过,所以自测永远绿。

来源:收口时顺手修的老毛病。播放条 bootstrap 后一直显示,但 music-on 类只在 syncPlayUI()(播放/暂停回调)里加;没点过播放的页面 body 从头到尾没有 padding,页脚被压住。同一轮还发现「问知识库」悬浮球 z-index 70 压在播放条 60 上——两个都 fixed 在底部。

验证状态:⭐⭐ 同族第二次 —— 成稿链接存进库没人读_写入方不等于展示方_v1 与 零路由补路由_普查要能推翻已写的代码_v1 里的「初值方不等于渲染方」之后,这是第五个形态:不是「状态没人写」,而是「写了,但触发条件绑在了错误的生命周期上」。

操作规则:

  1. fixed 元素的高度用 ResizeObserver 量出来写回 CSS 变量(--mp-h),body padding、浮层 bottom、面板 height 全部由这一个变量推导。
  2. 钩子挂在「元素从 hidden 变可见」那一刻,不挂在任何交互回调。
  3. 验收要挑一个从没交互过的新 session:music-on 是否已有、--mp-h 是否为真值、页脚 bottom 是否 ≤ 条 top。

反例/边界:纯交互态样式(hover、:active、播放中的进度条)本来就该挂在回调上;判断标准是「这段布局缺失时,页面是否结构性错误」——是,就必须与交互解耦。

失败后的重试节奏,必须由外部事件驱动,不能由定时器驱动

核心:「失败就留着队列等下一轮」听起来是稳健,实际是给故障加了一个恒定频率的放大器。

来源:P1 首版。合批窗口 1.5 秒,失败即重排;服务端 5xx 时变成每 1.5 秒一次 POST,单个客户端就是小型自我 DDoS,而且会把「服务端挂了」这件事掩盖成「服务端很忙」。

验证状态:⚠️ 首次发现。与库内「保活心跳不能搭业务轮询的便车」同族,但方向相反:那条讲「别把必要的写搭在不必要的轮询上」,这条讲「别把不必要的重试绑在固定定时器上」。

操作规则:

  1. 失败只置状态(徽章变「失败可重试」),不重排定时器。
  2. 补传的触发点选本来就高频且语义正确的事件:用户勾选、online、visibilitychange、登录态变化、点徽章。
  3. 定时器只负责合批(短窗口),不负责重试。

反例/边界:幂等且极便宜的探活(心跳、版本号轮询)可以固定间隔;涉及写入的一律不适用。

同步层与存储层分离到「请求函数由外部注入」

核心:把网络层写成不 import 任何 DOM 依赖的纯模块,请求函数当参数传进来,同一份代码就能在 node --test 里跑,不必为它拉起浏览器。

来源:P1 第一版把 account-core.js 直接 import 进来取 token,node --test 里因为没有 document 直接炸;改成 request 注入后,15 个同步用例(含「请求在飞途中再勾一次」)全部在 node 里跑完,单文件不到 1 秒。

验证状态:⚠️ 首次发现。

操作规则:

  1. 网络层只依赖三个注入项:request(method, path, body)、storage、online()。
  2. 浏览器专属能力(localStorage、navigator.onLine、document.visibilityState)由调用方包装后传入;测试里换成内存实现。
  3. 想在测试里卡住「请求在飞」这一刻,用 gate(promise 未 resolve)而不是 setTimeout 猜时间。

反例/边界:强依赖框架生命周期的逻辑(路由守卫、框架状态管理)硬拆反而更脆;拆的判据是「这段逻辑是否需要在没有浏览器时被验证」。

下线一个版块:先摘入口,不删链路

核心:版块「不用了」和版块「不能存在了」是两件事;前者要的是可逆,后者才需要拆链路。默认按前者做。

来源:任务书降级。没有删表、没有删接口、没有删管理台,只加了一个 features.js 开关把入口全部收起(/tasks/ 变成暂停说明页,详情页 getStaticPaths 返回空)。24 小时内这个决定就被验证有用:第二天讨论「以后可能还有用」时,成本是改一个布尔值。

验证状态:⭐⭐ 同族第二次,方向相反。公屏下线只删了界面_删界面不等于关链路_v1 讲的是「以为关掉了其实没关」;本条讲「以为要拆掉其实只需要关」。共同点:下线深度由「你怕什么」决定,不由「代码看起来该不该留」决定。

操作规则:

  1. 决策先问一句:这是合规/安全要求,还是产品优先级调整?后者一律走开关。
  2. 开关要有单一真相源,并镜像到构建期环境变量,避免「代码里关了、产物里还开着」。
  3. 开关收起的范围要列全:导航、首页速览、关于页计数、llms.txt、sitemap、详情页路由、账号页入口——漏一处就是半开。

反例/边界:涉及隐私、法律、资金的功能必须真拆(接口 404,不是 401 也不是隐藏按钮);开关不适用。

测量工具本身要先被证伪(又一次)

核心:「页脚被压住」的结论用了两轮才成立,两次都是工具在说谎,不是页面在说谎。

来源:收口验证。第一次用 window.scrollTo(0, scrollHeight) 后立刻量 getBoundingClientRect(),站点有 scroll-behavior: smooth,量到的是动画中途 → 误判「仍被压住」;第二次用元素级截图(locator.screenshot()),fixed 播放条被画进元素的框里 → 看着像压住,实际拍视口是好的。改成 behavior: 'instant' + 等一帧 + 拍视口/量数值,才拿到真结果。

验证状态:⭐⭐ 二次验证全站文字截断体检_检测工具本身要先被证伪_v1 的核心律——那次是判据里一个拍脑袋的常数把正常元素判成缺陷,这次是时序与截图坐标系。

操作规则:

  1. 量几何量之前先让页面静止:滚动用 behavior: 'instant' 或显式等 scrollend。
  2. fixed 元素不要用元素级截图判定是否遮挡,用两个 rect 的数值比较。
  3. 结论与直觉相反时,先怀疑工具,再怀疑页面。

反例/边界:纯静态页(无 smooth scroll、无 fixed 元素)可以直接量;有动效或 fixed 层时一律不适用。

下次改进

如果重来,最想改哪一步:不是技术顺序,是开工前没定义”什么算被验证过”。

这次四段全部「上线 + 测试全绿」,读起来很顺;但把真实用户数填进事实区之后,结论只有一句:8 个学习项、0 个真实用户、所有断言来自自测。功能是对的,证据是薄的。如果一开始就把「验收 = 至少一个非作者账号在另一台设备上完成一次真实读取」写进计划书,这两天的收口会诚实得多,也不会让「已同步」的徽章在只有测试数据时显得像成果。

下次同类型任务的行动清单:

  1. 开工第一张表写数据模型与主键,不写页面。
  2. 给主键写台账测试,让「改 ID」变成 CI 红,不是 code review 靠眼睛。
  3. 任何「本机为空 → 落默认值」的分支,先标一句注释「此处等首轮远端回来再写」。
  4. 给 fixed 元素留位的 CSS 变量,挂在元素可见那一刻;验收用一个从未交互过的 session。
  5. 失败路径只置状态;把重试挂在真实用户事件上。
  6. 上线当天就把「真实用户数 / 真实设备数」记进事实区,别等复盘时回忆。

附记:三处只在真跑时才现形的坑

现象真因判据
