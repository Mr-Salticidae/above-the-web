手机 HDR 视频交付 · 三层分离与体积先定

入档:2026-11-20 来源:《虚拟游戏》过本单讲解视频（手机录制，15:26 / 3.83 GB）压缩并回传手机端上传 状态:⚠️首次 · 单案例，机理已确证，配方在本机跑通

一句话

手机录的 HDR 视频交不出去，卡住人的从来不是「压缩」这一个动作，而是色彩层、兼容层、体积层三层叠在一起；更贵的一课是——体积目标必须由人先定，压完再改等于整遍白跑。

事实经过

项源成品
体积3.83 GB169.2 MB（压缩率 95.7%）
规格1080×1920 竖屏 / 30fps / HEVC 10bit · HLG 杜比视界 / 35.5 Mbps1080×1920 / 30fps / H.264 High · SDR BT.709 / 1.53 Mbps / AAC 128k
时长15:2615:26（一帧不差）

过程里两次返工，都不在画质：

  1. 先按 6 Mbps 编码（预计约 700 MB），跑了十分钟被一句「还是太大，不好传输」叫停，中间产物全部废弃；改问目标体积后选「约 180 MB」，重出 1.4 Mbps 版。
  2. CPU 版 zscale+hable 加两遍编码十分钟未完，换 GPU libplacebo 单遍约五分钟完成，同码率画质肉眼一致。

一个是「先动手后定约束」，一个是「算力花在错的路径上」。

三层分离：别把三件事当成一件

层病灶不处理会怎样处理
色彩层HLG / 杜比视界 HDR微信、Windows 播放器、投屏整体发灰发暗，肤色不对色调映射到 SDR BT.709
兼容层HEVC 10bit老设备 / 部分微信环境打不开（缺解码器或硬解）转 H.264 High + yuv420p + AAC
体积层35.5 Mbps 原码率3.83 GB 传不动、上传超时按目标体积倒推码率

三层各自独立：只转 H.264 不做色调映射，颜色照样错；只压小不转编码，老设备照样打不开；只做前两层不问体积，可能压出 700 MB 仍旧传不动。

Mac素材包到Windows的两个坑_zip文件名编码与HEVC解码_v1 讲的是接收侧「两个坑叠满」（zip 文件名编码 + HEVC 缺解码器）；本篇是交付侧把坑扩成三层，并补上第三层「体积由谁决定」。两篇合起来才是完整的一条素材进出链路。

如何使用

第 0 步 · 先问目标体积，再动第一帧

体积是人的约束，不是技术参数。开口就问「压到多大 / 传给谁 / 走什么通道」，给两三个可选项让人挑。码率、分辨率、编码方式全由它倒推，选错就是整遍重来。不要先压一版再问。

第 1 步 · 取片与验明正身

  • adb devices -l 确认设备；adb pull /sdcard/DCIM/Camera/<文件> .
  • Git Bash 会把 /sdcard/... 自动转换成 Windows 路径 → 必须 export MSYS2_ARG_CONV_EXCL='*'，本地路径写 C:/... 风格。
  • ffprobe 看清 codec_name / pix_fmt / color_transfer / color_space / color_primaries / bit_rate / width×height / r_frame_rate 与旋转元数据。别凭文件名猜规格——这次名字带 DOLBY，实测却是 1080p 而非预想中的 4K，省掉了一步缩放。

第 2 步 · 色调映射先试帧，再定参数

三秒试片、抽一帧肉眼比两条链路：

链路滤镜本机实测
GPUlibplacebo=tonemapping=auto:colorspace=bt709:color_primaries=bt709:color_trc=bt709:format=yuv420p单遍约 5 分钟 ⭐
CPUzscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p两遍编码 10 分钟未完

本次两版肤色与暗部几乎一致，于是按速度选；有独显优先 GPU 单遍。色彩是「清单查不出」的东西，必须看帧，不能只看滤镜跑没报错。

第 3 步 · 按目标体积倒推码率，单遍直出

码率(kbps) ≈ 目标体积(MB) × 8 × 1024 / 时长(秒) − 音轨码率

本次 180 MB / 926 s ≈ 1.58 Mbps，扣 AAC 128k 后取 -b:v 1400k -maxrate 2000k -bufsize 4000k：

-vf "libplacebo=tonemapping=auto:colorspace=bt709:color_primaries=bt709:color_trc=bt709:format=yuv420p" \
-c:v libx264 -preset medium -b:v 1400k -maxrate 2000k -bufsize 4000k \
-profile:v high -level 4.1 -pix_fmt yuv420p -c:a aac -b:a 128k -ac 2 -movflags +faststart

竖屏人像讲解、背景基本静止，1.4 Mbps 在此类内容上接近透明；换题材（运动 / 游戏实录 / 特效）先试帧，别直接套码率。

第 4 步 · 回传与双校验

adb push "C:/.../成品.mp4" "/sdcard/Download/成品.mp4"——Download 是各类上传入口的文件选择器都能看到的落点。回传后做字节数 + MD5 双校验（本次两端同为 177,450,815 字节、42c6dff7…），再发 MEDIA_SCANNER_SCAN_FILE 广播，让相册类入口也能索引到。

验收三步

  1. 参数：ffprobe 核时长、分辨率、帧率、编码、音轨；时长必须一帧不差。
  2. 画面：抽前 / 中 / 后 3 帧肉眼验肤色、块状瑕疵、方向正立。
  3. 完整：手机端字节数与 MD5 同本机一致。

判据与红线

  • ⭐ 体积先于码率：目标体积由人定，技术在后倒推；压完再改 = 整遍重来。
  • ⭐ HDR 源转发前必须色调映射：这是色彩层，不是「播放器问题」，换播放器解决不了。
  • 不二次压缩：要更小就从源文件重出，不拿成品再压一次。
  • 原片不动：手机原片与本机源文件都保留，清理属破坏性操作，须明确确认。
  • 内容能用清单验收，呈现必须肉眼验收：与 图表交付的确定性_坐标绘制胜过自动布局_v1 同一条——参数全绿不代表画面能对。
  • ⚠️ 单案例。三层分离与「体积先定」可迁移；1.4 Mbps 这个数值只适用于静止背景的竖屏人像讲解，别当通用常量。
