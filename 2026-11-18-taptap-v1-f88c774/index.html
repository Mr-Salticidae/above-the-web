工位池塘上架 TapTap:手机与 PC 双端首发

入档:2026-11-18 来源:《工位池塘 Desk Pond》v0.7.1 上架 TapTap(开发者 542037「蛛网之上」/ app 1073282);本仓提交 d8d179b→f9fc1ac,蛛网之上提交 1b258c9 状态:版本审核中(audit 1294947),未上线,零真实用户

一句话

从「从没打过安卓包」到「APK + Windows 双端同时进审核队列」用了一天,真正卡住的不是打包,是三件我以为已经办好的事:以为勾了「通用隐私政策托管」就算交了隐私资质、以为 LOGO 只要好看就够大、以为改了 Godot 编辑器设置就会生效——三件都按字面做完了,三件都被打回或静默失效。

  • 提交区间:本仓 ea09d6d..f9fc1ac,5 个提交,18 files changed,+554 / −45;蛛网之上 6862abd..1b258c9,2 files,+229 / −1

  • 最终结果:两个包体同绑 revision 1294947;precheck-review → blockers: [] / preaudit_status: passed;submit-review → status: reviewing
  • 资质:适龄 8+ approved;AI 声明(不提供 AIGC 服务)approved;防沉迷 uploaded(走 TapPlay,submit_blockers: []);隐私合规 rejected → 重交,audit 495895

「4 次驳回」不是失败次数,是平台的判据被逐条问出来的次数。下面每条方法论都对应其中一次的原文。

回顾:四段,顺序本身就是信息

  1. 环境从零搭(无提交):Godot 安卓导出要 JDK + Android SDK。dl.google.com 直连与代理都不通(curl: (35) schannel),改走腾讯镜像手工摆出 platforms/android-36、build-tools/36.1.0、platform-tools;sdkmanager --licenses 拉不到源,手写 license 文件。绕完这些仍然报「SDK 路径无效」。
  2. 找到根因(3b70d22 附近):SDK 与 JDK 一直不生效,不是路径写错,是读的文件不是那个文件——Steam 便携版把编辑器设置放在安装目录 editor_data/editor_settings-4.7.tres,而我改的是 %APPDATA%\Godot\。改对文件后一次通过。
  3. 移动端改造 + 素材(3b70d22、82bf029):is_web 纳入 android、竖屏、全面屏安全区换算、弹窗在 400 设计宽下收窄;截图/图标/宣传图做成可重跑的 Godot 场景。
  4. PC 端叠加 + 资质返工(b911245、f9fc1ac、1b258c9):app_platforms 扩成 ["MOBILE","PC_OFFICIAL"]、声明 ["apk","windows"];隐私被驳回后去自有站补独立政策页;PC 四图与配置要求;最后机审 LOGO 不过,放大重做。

顺序不是最优的:正确顺序是先把「平台会怎么验」问清楚,再动手做素材。实际是先做完素材、被驳回了四次,才逐条摸到判据。

没有「获胜原因」可写——这不是比赛,也没有对照组。能写的只有「哪些判据被平台真的执行了」。

对照一:平台的「必填」清单 vs 我实际交的材料

隐私合规是 required,我选了「通用隐私政策托管」,系统显示已保存、预检只给 warning 不给 blocker,看起来齐了。结果独立资质审核打回:

隐私政策链接请勿为 TapTap 站内页面,请更换为独立网页链接。

我以为实际差别在哪
必填项填了 = 这项过关填了只是「有材料」,过不过是另一级审核提交资格(submission_eligibility)和资质审核是两层
通用托管 = 平台提供合规文案,省事托管产物是一个站内页地址,而规则要求「不属于本平台的网页」平台不接受自己域名下的页面当第三方承诺

解法不在 TapTap 里:去自有站加了 public/desk-pond/privacy.html,push 触发 GitHub Actions 构建 + rsync 到香港服务器,拿到 https://tiaozhuxiansheng.com/desk-pond/privacy.html 再把链接回填。

写政策前先核实事实,否则政策本身就是新的违规点。这轮用 aapt2 dump permissions 确认 APK 零权限声明;安卓端 is_web 为真、更新检查被跳过,所以「Android 版完全不联网」是能站住的断言,不是话术。

对照二:机审四次驳回,四次都在纠正「我以为的标准」

驳回原文我原本的做法真正的要求
除游戏标题外,请勿添加多余的副标题或说明文案宣传图上加了「你专注,它钓鱼」+ 三条卖点宣传图只能有标题
整体排版设计感不足,背景存在大面积单调留白深色底 + 小标题,留白当高级感留白在机审眼里是「没做完」,要满版构图
竖版封面图中包含了较多非游戏标题的界面UI及功能文字直接用了整屏实机截图封面是美术图,不是截图
游戏LOGO图案尺寸过小,使其占据画布60%以上的空间1280×720 上放一行 150px 字有数字阈值,量的是主体占画布比例

前三条是形容词,只能一版版试;第四条给了数字,一次就过。给数字的按数字改,给形容词的才按审美改——把形容词当数字猜,是我在第一条上浪费一轮的原因。

方法论沉淀

「必填」描述的是审核结果,不是可交的材料

核心:平台把某项标成 required,只说明「没有它一定过不了」,不说明「你交的这个它认」。必填项的可交形态往往由另一份规则决定,而那份规则不在必填清单里。

来源:隐私合规。选「通用隐私政策托管」后 has_saved_material: true、预检只报 warning,一路看起来顺畅;独立资质审核直接驳回,理由是链接必须是「独立网页」而非站内页面。

验证状态:⚠️ 首次(单平台单次)。

操作规则:

  1. 看到 required,先找这条会被谁在哪一级验证:平台自检 / 独立资质审核 / 人工。三级判据不同。
  2. 凡「托管」「代填」「模板生成」类便捷选项,先问产物落在谁的域名/账号下;要求第三方承诺时,产物必须在自己能控制的域上。
  3. 预检的 warnings 不等于可忽略:QUALIFICATION_INCOMPLETE 这条 warning 从提审前一直报到提审后,它说的就是真话。

反例·边界:平台自有、且明确说明「由平台承担」的项(如走 TapPlay 的防沉迷)可以直接用托管;判断标准是责任主体是不是平台。

机审给数字就按数字改,给形容词才按审美改

核心:同一轮里被驳回四次,唯一一次「读数字、改一次就过」的是 LOGO(占画布 60%);另外三次都是形容词(「设计感不足」「多余文案」),每次都只能猜着重做一版。

来源:宣传图两版、竖版封面一版、LOGO 一版。LOGO 从「1280×720 上 150px 一行字」改成「512px 图标(占高 71%)+ 124px 名称横排(整体宽 83%)」后 preaudit_status 立刻 passed。

验证状态:⚠️ 首次,但同一轮内四个样本互为对照,可信度高于普通单例。

操作规则:

  1. 拿到驳回先分类:含数字/比例/尺寸 → 当硬阈值算,拿画布尺寸反推目标像素;不要顺手再改审美。
  2. 只给形容词 → 说明判据没公开,这时改的方向应该是「更像同类已过审的样本」,而不是「更符合我的审美」。
  3. 出图脚本里把阈值写成常量并在生成时打印实际占比(print 一下主体宽高),下次驳回能立刻自证。

反例·边界:数字阈值也可能量的是「不透明像素的包围盒」而非视觉重心,带透明边的素材要按包围盒算,不按画布算。

「改了没生效」,先确认程序读的是不是另一个文件

核心:同一份配置在系统里有不止一处可写位置时,「我改了」和「它读了」是两件事;报错信息只会说「无效」,不会说「你改错了文件」。

来源:Godot 安卓导出持续报 SDK/JDK 路径无效。真实原因:Steam 便携版不读 %APPDATA%\Godot\editor_settings-4.7.tres,读的是安装目录下 editor_data/editor_settings-4.7.tres。改对文件后,连之前「中文路径不被识别」的表象也一并消失(那只是第二个错误叠加)。

验证状态:⚠️ 首次。与库内「功能开关要接在能力被验证过上,不能接在配置填了上」同族,但形态不同:那次是没验证,这次是验证了错误的对象。

操作规则:

  1. 便携版/绿色版/多副本共存的软件,先确认「它到底读哪个文件」——找 --help、portable 标记、或直接改一处再观察文件 mtime。
  2. 报错说「路径无效」时,先验证「我改的这份配置有没有被读」,再验证「路径本身对不对」。顺序反了会一直改到对为止却不知道为什么对。
  3. 改完立刻用一个只依赖该配置的动作验证(这里是导出一个空包),不要等全流程跑完才发现。

反例·边界:单一安装源、单一用户配置目录的软件没有这个问题;只要有「安装目录 + 用户目录」双份配置,一律适用。

平台写接口的 expected,是漂移检测不是权限墙

核心:read-before-write 要求把字段当前值原样回填,不是刁难,是防「你以为你在改 A,其实 A 已经被别人改成 B」。绕过它(force: true)等于自愿放弃这个保护。

来源:更新 PC LOGO 时先报 409 字段已被外部修改或缺少 expected。按提示先 get-module --data '{"module_id":"windows-exclusive"}' 取 current_value 原样回填,一次成功。同一轮还踩了它的反面:app_platforms 在提审中被拒(400「游戏资料已提交或已过审」),因为提审即冻结。

验证状态:⚠️ 首次。

操作规则:

  1. 改任何字段前先读所属模块的 current_value,连同 info(尺寸/字节/均值色)一起回填——只回填一半也会被判漂移。
  2. 409 不要用 force 兜底;先比对「当前值」与「我上次写的值」是否相同,相同说明是我自己上次写成功、这次重复了。
  3. 写接口的必填参数也是判据:release_schedule.kind 只接受 immediate / scheduled_exact,传 "" 直接 400——文档示例里的空字符串不能照抄。

反例·边界:读到的值与目标值已经一致时,不要重写;重写会产生一次无意义的修订。

提审即冻结:改资料的代价是重新排队

核心:内容审核期间所有资料字段只读,想改必须 withdraw-review 撤回,撤回后版本回到 draft,之前排的队作废。

来源:先提审了手机版(audit 495873),随后要加 PC 端,save-changes 报 400、create-draft 报 422(需先撤回)。撤回后重提,audit 变成 1294947。

验证状态:⚠️ 首次。

操作规则:

  1. 提审之前把机审预检跑绿(preaudit_status: passed + blockers: []),机审不是提审的前置条件,但它是唯一能在冻结前告诉你「会挂」的免费检查。
  2. 多端/多包体一次性想清楚再提;「先发一个、再补一个」在这个平台上的代价是撤回重排。
  3. 撤回前先确认「重提需要什么东西重新上传」,不要撤回后才发现素材也得重来。

反例·边界:纯文案的错别字级改动,如果平台允许审核中留言给审核员,优先走留言;冻结规则主要卡的是结构化字段。

下次改进

如果重来,最想改哪一步:不是环境搭建,是在写第一版宣传图之前,先把平台上同类游戏的商店页翻十张。

这次四次驳回里有三次(宣传图两版、竖版封面一版)属于「不知道这类图长什么样」。判据其实一直公开——商店页上全是过审的样本,只是我先动手做了。机审驳回的形容词不是随机挑剔,它对照的是一批同类样本的中位数。

下次同类型任务的行动清单:

  1. 开工第一件事:把目标平台同类游戏已过审的素材各存 10 张,不是看规范文档,是看成品。
  2. 环境类报错,先验证「配置有没有被读」,再验证「配置写得对不对」。
  3. 素材类驳回,先分「带数字」还是「带形容词」,只有后者才需要审美迭代。
  4. 素材生成脚本里把平台阈值写成常量并打印实际占比,让驳回可自证。
  5. 涉及多端/多包体,一次性想齐再提审;提审前跑预检,不把提审当保存。
  6. 写任何合规文本前,先用工具证实事实(权限清单、网络行为),再落笔。

附记:只在真跑时才现形的坑

现象真因判据

续篇:2026-11-20 第五次驳回 —— 解析名与详情页标题不一致

性质:原文事实区冻结于 11-18,本节是事后补丁,不改上面的结论。 状态:已修复并重提审(status: reviewing),审核结果未出。

驳回原文:1. 游戏解析名【Desk Pond】与详情页标题【工位池塘】不一致。 两个包都带同一条 reject_reason(APK 与 Windows 包各一份),说明不是某一端的问题,是包体解析结果与商店资料的对账。

新增的核心律:包体「解析名」和引擎「内部名」是两层,改前者不要动后者。

层字段原值新值验证步骤
APK 解析名export_presets.cfg 的 package/nameDesk Pond工位池塘aapt2 dump badging → application-label,并检查全语言 label 无残留
Windows 解析名同文件 application/product_nameDesk Pond工位池塘PowerShell (Get-Item *.exe).VersionInfo.ProductName
运行时窗口标题scripts/main.gd _ready()继承 config/nameget_window().title = "工位池塘"启动后看任务栏/标题栏
引擎内部名(不动)project.godot 的 config/nameDesk Pond保持不变%APPDATA%\Godot\app_userdata\Desk Pond\ 存档目录仍是原来的

最后一行是这次最该记住的判断:config/name 决定 Godot 的 user:// 落到哪个目录。为「让名字统一」直接把它改成中文,自有站桌面版老用户的存档会静默读不到(不是丢文件,是新版本去了一个空目录)。而审核要的「解析名」来自包元数据(manifest label / PE 资源),跟 config/name 根本不是一回事——按驳回字面去全局替换字符串,会顺手制造一个比驳回严重得多的事故。

换包的连锁副作用:重新上传 Windows 包并绑定槽位后,pc_game_anti_addiction_status(PC 防沉迷状态,other-settings 模块的 required 项)被清空,预检立刻报 MISSING_REQUIRED;而四张 PC 图与 min_os / min_processor / min_memory / min_storage 全部保留。所以换包之后必须重跑预检并逐项核对必填字段,不能假设「只换了包,资料没动」。补齐后 blockers: []、preaudit_status: passed。

这轮补进行动清单的一条:包体改名/重传后,① 用解析工具(aapt2 + .VersionInfo)自证新包的名字,不靠「我改了源文件」;② 重跑预检查必填字段;③ 递增 version/code(1→2)避免同包名同 code 的覆盖歧义。

验证状态:⚠️ 首次(单平台单次)。与上一条「机审给数字就按数字改」同族——这次驳回给的是逐字字符串,照字面能定位到具体字段,比形容词好办;难的是判断「改哪里」而不是「改成什么」。
