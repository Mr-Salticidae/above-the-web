## 作品回顾

### 创作思路（当时想做什么）

这一轮同时解决三个痛点：

1. **发任务必须改 markdown 太慢** —— 每次发任务都要开编辑器、改 md、push、等构建。想做到「在管理台填完就生效」。
2. **管理台一页堆太多东西** —— 待处理申请、任务列表、账号管理、操作记录挤在一页，越加越不清晰。
3. **定人后调报酬没地方落账** —— 报销会员费、加急费这类临时加价，改 md 会被下一轮同步覆盖回去。
4. **首页太长、进站第一眼是卡片墙** —— 362 篇笔记全铺在首页底部（134 KB / 218 KB），占了整页八成篇幅。

### 执行过程（实际怎么做的）

**任务书系统**（`0a473e4`）：
- `tasks` 表加 `source` / `body` 两列，老库走 `ALTER TABLE` 迁移
- 同步逻辑只碰 `source='md'` 的行，站内新建的不参与下架判定
- 详情页拆成两份：md 走静态页，站内新建的走 `/tasks/detail/?slug=` 动态页
- 正文渲染用新写的 `mini-markdown.js`（~140 行），先转义再拼 HTML，`javascript:` 链接当文本落地

**管理台拆分 + 调价**（`b6ed9c4`）：
- 抽 `AdminLayout.astro` 做共用壳（标题 + 板块导航 + 权限门禁）
- 门禁逻辑收进 `admin-core.js` 的 `bootAdmin()`
- 六页各司其职：概览 / 申请 / 任务 / 新建 / 账号 / 记录
- 调价：`fee_override` / `fee_note` 两列，同步不碰；对外接口 `fee` 永远是「现在到底结多少」

**首页瘦身**（`ce86599`）：
- 362 篇笔记搬去 `/notes/` 独立成页，首页只留七个栏目入口
- 分栏与计数逻辑抽进 `lib/note-groups.mjs`，首页与 /notes/ 共用
- 滚动渐现抽进 `scripts/reveal.js`，样式收进 `global.css`
- 刊头 `.masthead*` 三页重复副本收进 `global.css`

### 最终输出

| 模块 | 上线产物 |
| --- | --- |
| 任务书 | 站内新建 → 列表卡片 → 动态详情页 → 认领 → 流转，整条路跑通 |

## 结果分析

### 我的方案做到了什么

- **任务书的「双源头」设计**：md 与 `web` 两种来源共用一张表、一套流转，同步只碰 md 那份。这避免了「站内新建的任务被清单误下架」这个坑。
- **调价独立于任务书**：`fee_override` 是运行时状态，md 里写的是原价。导出 md 时写原价——任务书是任务书，这次结多少是这次的事。
- **管理台共用壳**：门禁、导航、`slot` 分发集中在一处，六页各自只管内容。
- **首页与 /notes/ 共用分组逻辑**：`note-groups.mjs` 一份数据两处用，计数不再各算各的。

### 我的方案没做到什么（边界）

- **mini-markdown 只认一小撮语法**：表格、脚注、嵌套列表没做。这是有意为之——写到那个份上，本来就该落成 git 里的 md。但边界卡在哪：如果发布方想在任务书里放一个对比表，现在做不到。
- **调价「加减」算法靠正则找第一个数字**：遇到「约 100-150 元」这种区间会算错。当前用「直接写新报酬」兜底。
- **首页栏目瓦片没带最新一篇**：只显示篇数和定位，没露出该栏最新一篇的标题，缺一点「正在更新」感。

### 结果符合预期吗

**全部达到**：四个预期目标（站内发任务 / 管理台拆分 / 调报酬 / 首页瘦身）都上线跑通。

## 方法论沉淀

### 双源头数据模型（source 字段）

**核心**：同一张表里的行可以来自不同源头，同步/下架逻辑必须按来源分流，否则「清单里没有」会被误判为「被删了」。

**来源**：任务书 md 与站内新建的对接——清单里没有站内任务，不代表 md 被删了。

**验证状态**：⚠️ 首次发现（本次迭代触发，还没在别的场景验证过）

**操作规则**：
1. 表加 `source` 列（`md` / `web`），所有同步逻辑都带 `WHERE source = 'md'`
2. 站内新建的行不参与「清单里没有 → 下架」的判定
3. 反过来，md 补上同名 slug 时自动接管正文，运行时记录（认领、打款）保留

**反例/边界**：如果同一个 slug 在 md 和 web 同时存在，md 优先（md 是真相源，web 是草稿态）。

---

### 运行时状态与真相源分离

**核心**：任务书正文是真相源（git），调价/定人/交付是运行时状态（数据库）。两者改的频率、时机、回滚方式完全不同，存在同一张表但要分列管理。

**来源**：调整报酬 —— 改 md 既慢又会被同步覆盖。

**验证状态**：⚠️ 首次发现

**操作规则**：
1. 真相源字段（title / summary / fee / deadline）归同步覆盖
2. 运行时字段（status / taker / fee_override / fee_note）同步一律不碰
3. 对外接口的「展示值」= COALESCE(运行时, 真相源)，页面不用各自判断

**反例/边界**：导出 md 时只写真相源，运行时状态不进 git。

---

### 管理台一件事一页

**核心**：管理台是工具页不是展示页，一件事一页 + 共用壳（门禁/导航/slot），比一页堆所有内容更清晰。

**来源**：管理台从一页拆成六页。

**验证状态**：⚠️ 首次发现

**操作规则**：
1. 共用壳只管：标题、板块导航、权限门禁、`slot` 分发
2. 各页只管：自己的数据、自己的交互、自己的提示
3. 门禁逻辑集中（`bootAdmin()`），别散落在各页

**反例/边界**：如果两页之间需要共享大量状态（比如跨页的选中项），一页可能更好。这次六页各自独立，没有这个问题。

---

### 首页是入口，不是仓库

**核心**：首页回答「这站有什么」，不回答「这站的所有内容是什么」。全部内容进子页，首页只给入口。

**来源**：362 篇笔记搬离首页。

**验证状态**：⚠️ 首次发现

**操作规则**：
1. 首页每个板块：最新一期/几篇 + 入口链接
2. 子页承载完整索引（筛选、分栏、计数）
3. 首页与子页的分组逻辑共用一份数据源，别各算各的

**反例/边界**：如果某个板块内容极少（< 5 篇），可以考虑直接在首页露出。这次笔记 362 篇必须搬。

---

### 浏览器侧渲染的安全基线

**核心**：内容进过数据库，就不再是「自己写的字符串」——先转义再拼 HTML，链接白名单只放行安全协议。

**来源**：站内新建任务书的正文存库，浏览器侧渲染。

**验证状态**：⚠️ 首次发现

**操作规则**：
1. 所有进过数据库的富文本，渲染前先 HTML 转义
2. 链接白名单：`/`, `#`, `http(s):`, `mailto:` 放行，其余（`javascript:` 之流）当普通文本落地
3. 图片 `src` 同样走白名单

**反例/边界**：如果未来要支持站内富文本编辑器（带格式按钮），这套 mini-markdown 不够用，得上完整 markdown 引擎。当前任务书场景够用。

## 下次改进

### 如果重来，最想改哪一步

没有特别后悔的。三个大方向都做到位了。

### 下次同类型任务的行动清单

1. **双源头模型**：再遇到「同一个东西两个来源」时，先问「哪个是真相源、哪个是运行时」，再动手建表。
2. **首页瘦身**：新增任何板块时，先想「这该进首页还是进子页」，默认进子页。
3. **管理台扩展**：再加新页时，先往 `AdminLayout.astro` 的 NAV 数组里加一项，再新建页面文件。
4. **调价算法**：下次如果报酬格式更复杂（区间、多币种），把「加减」改成「直接写新报酬」为主、加减为快捷入口。
5. **mini-markdown**：如果任务书正文需求涨到需要表格，评估是升级渲染器还是引导用户落成 md。
