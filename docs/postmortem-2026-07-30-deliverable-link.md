## 方法论沉淀

### 1. 写入方不等于展示方

**核心**：一个字段有人写、有库存、接口也返回，不等于有人读它。链路上任一环没接，功能就等于不存在。

**来源**：`deliverable_url` 写入路径三条（承接人提交、管理台手填、同步初值），读路径零条。

**验证状态**：⭐⭐ 二次验证。同族前两例——「写入方不等于推进方」（状态字段有人写、有人显示，没人在到点推进它）、「界面演完不等于链路存在」（报名界面全在，`submissions` 表 0 行）。本轮是第三形态：**存进库不等于看得见**。

**操作规则**：
1. 加运行时字段时对照三件套：**存库 → 接口返回 → 页面渲染**，缺一条就是隐形字段；
2. 读路径要挂在**收敛后的那个字段**上（`tasks.deliverable_url`），不是某一条写入口的流水表（`deliveries`）——流水表只记「谁在什么时候提交过」，不回答「现在的成稿是哪份」；
3. 验收问句从「数据存进去了吗」改成「**页面上哪一行会因此变化**」。

**边界**：只写不读也可能是对的（审计、留痕类字段本就不上页面）。判据是「这个字段存在的目的是给人看吗」。

### 2. 手工兜底会掩盖缺失的系统路径

**核心**：人用手写内容替系统把事做了，缺口就永远暴露不出来。

**来源**：前三份任务书都在正文里手写了「交付情况 + 成稿链接」，页面看起来一直是对的。

**验证状态**：⭐⭐ 二次验证。前例是「手动跑通会掩盖自动路径」（云端定时内容生产：人先手动跑通一遍，掩盖了自动路径的坑）。本轮是它在**内容层**的形态。

**操作规则**：
1. 发现某个功能「靠人手写补上」时，记一笔——那是系统缺口的位置，不是工作习惯；
2. 新增字段后，**至少走一遍不靠手写的路径**（本轮就是「只在管理台填，正文一个字不改」）。

**边界**：手工兜底本身没错，它是上线速度的合理代价；错的是把兜底当成常态而不记账。

### 3. upsert 两条分支的字段集要对齐

**核心**：`INSERT` 写了某列、`UPDATE` 没写，表现为「只有第一次同步生效」——最像「同步不工作」，实际是分支不对称。

**来源**：`syncTasks` 的 `INSERT` 带 `deliverable_url`，`UPDATE` 不带。

**验证状态**：⚠️ 首次发现。

**操作规则**：
1. 改 upsert 时把两条分支的列清单**并排列出来**比对，不逐条读代码；
2. 真相源字段与运行时字段混在一张表时，`UPDATE` 分支用 `CASE WHEN <列> = '' THEN ? ELSE <列> END` 表达「只在空时回填」，比在应用层判断更难写错。

**边界**：确实该「只入库一次」的列（`created_at`）本就不该出现在 `UPDATE` 里。

### 4. 运行时字段的验收要造出「真相源与库不一致」的那一格

**核心**：md 与库一致时，看不出到底是谁在生效。验收必须造出不一致的状态。

**来源**：本轮自测造了三格——md 无链接 / 库里有（管理台手填，就是用户踩的场景）；md 有链接 / 库里空（应隐藏，证明库为准）；两边一致（应显示）。只有第二格能证明「数据库为准」这条设计真的成立。

**验证状态**：⚠️ 首次发现。

**操作规则**：
1. 双源字段的验收矩阵至少三格：**只有真相源、只有库、两边都有**；
2. 造状态用临时库 + 管理台接口，不要动生产数据。

## 下次改进

**如果重来，最想改哪一步**：`a179002` 加 `deliverable_url` 时就该问一句「哪个页面读它」。当时详情页只渲染了 `deliveries`，看起来「成稿链接已经有地方显示了」，实际显示的是另一条路径的产物。

**下次同类型任务的行动清单**：

1. 加运行时字段 → 当场写下「存库 / 接口 / 渲染」三行，缺哪行就补哪行，不留「以后再接」；
2. 改 upsert → 并排比对 `INSERT` / `UPDATE` 的列清单；
3. 验收双源字段 → 造出「只有库里有」那一格再签收；
4. 看到正文里手写的系统信息（状态、链接、日期）→ 记为待补的系统路径。
