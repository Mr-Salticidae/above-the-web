钉钉逐字稿补写：「过渡话术」是占位符不是待办 + 案例引言体例

入档：2026-09-15 来源：《WorkBuddy全案实战汇总》（alidocs adoc，nodeId P0MALyR8kl1Nm0okIYARqww7W3bzYmDO）逐字稿补写 4 处：案例 7 / 案例 12 前置引言、第四章前过渡话术、视频网页类板块过渡话术 验证状态：✅ 当场验证（3 次倒序插入 + 2 次 JSONML 原地改写，每次 range 读回校验顺序与 mention 完好；写入前各存 version-save 快照 17222 / 17225 / 17228 / 17229）

一句话总结

教程序列文档里写着「过渡话术」四个字的段落，是作者预留的槽位，不是留给 AI 的任务说明——接到”在 XX 之前补一段过渡话术”时先读区间，槽位往往已经在那儿，正解是原地改写而不是再插一段；且这类槽位普遍挂着 @某人 mention 标注责任人，改写必须把 mention 原样拼回 JSONML。配套的是逐字稿案例引言的固定骨架：承上启下 → 传统做法对比 → 本节定位 + 步骤数预告 → 成品展示句 → 制作步骤。

一、⭐ 正文里的「过渡话术」= 作者留的槽位

用户说「在第四章开头之前补一段过渡话术」。读区间后发现：目标位置已经存在一个段落，正文就是「过渡话术」四个字，位于案例22 末尾、第四章 h4 标题正上方。

这是作者（及协作人）的留位习惯：先把位置占住，内容后填。同一篇文档里两处都这么写。

判据与处置：

  1. 接到「补一段 XX」类需求，先读目标区间再动手，不要默认没有；
  2. 命中槽位 → block update 原地改写（保留块 uuid 位置语义），不是再插一段——插新段会留下「过渡话术」四个字，且正文变成两段重复内容；
  3. 全文占位可能不止一处，用 +fetch --scope keyword --keyword "过渡话术" 一次捞齐，本次即两处；
  4. 槽位块普遍带 mention（本次两处都是 @郑垚(图图)，作者用来标注该段由谁负责）。改写时：
    • 先 +fetch --scope range --start-block-id <BID> --end-block-id <BID> --detail full 取原始 JSONML；
    • 把 data-type:"mention" 的 span 原样拼回新节点（放在最前），末尾换成新文本；
    • block update --content-format jsonml --fix-jsonml --element '<数组>'。
    • 合并进 dws块级插入_index语义陷阱与倒序插入法_v1 已有判据：要留 inline 属性（highlight/mention/链接）→ JSONML 通道；要清空格式 → --content。

与 AI查询召回失准_容器词自指与命中率区分度_v1 同源的一类误判：「过渡话术」在别处是任务说明，在这篇文档里是最强结构信号——它指的就是”这段还没写”，且往往就是用户口中的目标位置。

二、逐字稿「案例前置引言」的骨架（可直接套用）

用户给的原话是「案例只有内容没有引入，无法作为逐字稿朗读，参考它之前的几个案例是如何书写的」。正解是先抽出相邻 2~3 个案例的引言骨架再套用，不要凭空写。

从该文档案例 5 / 6 / 8 抽出的四段骨架：

段序作用句式
① 承上启下接上一个案例/板块，点出本节的差异「上一节我们……解决的是「X」。但……还有一类更费时间的活：……」
② 传统做法 vs WorkBuddy制造对比，说明省在哪「传统做法是 A、B、C，来回折腾大半天。而在 WorkBuddy 里，你只要……它就能……」
③ 本节定位 + 步骤数预告直接衔接「制作步骤：」「这一节我们就从这个页面出发，看……是怎么做出来的，一共 N 步。」
④（原有）成品展示句「这是用 XX 制作的……」已存在，不动

落位规则决定朗读顺不顺：

  • ①② 插在标题下空段（图片位）之后、成品展示句之前——空段是成品截图位，文字不能插到图和标题之间；
  • ③ 插在成品展示句之后，让它直接衔接下一行「制作步骤：」，念下来是「一共四步 → 制作步骤：第一步……」；
  • 同锚点插多段一律倒序插入（先插②再插①），本次第三次验证成立。

数字必须对齐正文计数源 ⭐ 二次验证

③ 里的「一共 N 步」必须往下数实际步骤标题再填（案例7 四步：输入需求/检查数据来源/检查可视化数据/发布网页；案例12 四步：输入需求/检查初稿/优化与完善/生成永久链接）。

这是 dws块级插入_index语义陷阱与倒序插入法_v1「铁律二：数字类错误必须对齐计数源」的跨场景二次验证——那边改的是既有错误数字，这边是新写内容也要按计数源填，同一个失效模式（凭印象写数字）。

三、板块/章节过渡段的写法：只推差异，不复述方法论

两处过渡话术的写作要点：

  1. 先读上一板块的收束句，看它已经讲过什么。本次案例11 结尾已把「说、做、看、改」讲完并预告了「后面视频、网页类实战，节奏也按这套来」，所以板块过渡不能重复方法论；
  2. 只推一个差异维度：视频网页类 = 交付形态变了（从”自己用的文件”变成”有链接就能分享的网页”）；第四章 = 谁先开口变了（从”你发一句它干一次”变成”你不提醒它也按时干 / 换设备接着干 / 没想法它帮你想”）；
  3. 上一节已讲完的方法，用一句「方法不用换，差别只在……」带过；
  4. 结尾落在引出下一章标题，把揭晓权留给下一章已有的开场白（第四章本来就有「那么 WorkBuddy 都有哪些高阶玩法呢？」），避免同一件事说两遍。

四、工程层（本机 Windows 环境，本次固化）

  • PowerShell → Python 传中文参数有编码风险：把待写入文本硬编码进 UTF-8 的 .py 脚本，PowerShell 只负责 python script.py，不传中文参数。含转义的脚本一律落文件（同旧档「bash heredoc 吃反斜杠」同族）。
  • 每批写入前单独跑一次 +version-save（不要塞进批量循环，stdout 可能为空拿不到 savedVersion）。本次 4 批 4 个快照号。
  • 写入后读回必做：doc read --content-format jsonml --scope range --start/end-block-id 按块区间取文本校验；刚写入常返回「文档内容尚未就绪」，sleep 10~15s 重试即可。
  • 本环境 Bash 工具 shim 坏了（dirname: command not found / GNU 命令缺失），一律走 PowerShell 调 Python；Python subprocess.run 必须显式 cwd=r"C:\"。
  • dws 是 sh 脚本，Python 里直调： node = C:\Users\Administrator\.workbuddy\binaries\node\versions\22.22.2-3\node.exe（目录带 -3 后缀） dws.js = ...\node\cli-connector-packages\node_modules\dingtalk-workspace-cli\bin\dws.js

五、一句话结论

见到「补一段 XX」先读区间——占位符可能已经在那儿，改写而非新增，且 mention 是作者的责任标注不能丢；逐字稿引言按「承上 → 对比 → 定位+步骤数 → 成品句 → 制作步骤」填，步骤数往下数正文；过渡段只推一个差异维度，不重复上一节已讲的方法论。

如何使用

  • 下次给钉钉逐字稿补开场/过渡：先 +fetch --scope keyword --keyword "过渡话术" 扫占位，再抽两个相邻案例骨架，按倒序插入 + 原地改写两条通道执行；
  • 任何「正文里像任务说明的短句」（过渡话术 / 待补 / TBD）都先当成结构信号读一遍区间；
  • 新写内容里出现的数字（步骤数、案例数）一律回正文数一遍再落笔。
